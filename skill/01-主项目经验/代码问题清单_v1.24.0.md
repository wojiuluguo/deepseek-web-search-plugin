## 二、高严重度

### 问题 1：采集链挂死（网易云歌曲页 / 番茄书页，同签名两例）【未根治】

**现象证据**：
- `--url music.163.com/song?id=186016`：stderr 仅 1 行选路日志，>15 分钟无输出，python 进程 CPU≈0（纯等待），Harvest→chain 全链无进展（downloads/_stress_v123/t3b_music 记录）
- `--url fanqienovel.com/page/7069948840148732967 --media-type text`：同签名挂死（downloads/_stress_v124/fanqie 记录）；静态 HTML 的 352 个"第X章"链接解析正常——**目录不是问题，挂点在打开后的某步**
- 共同点：都是重 JS / iframe 渲染页；B站/抖音/微博等同样复杂的页面同轮压测全部正常收口

**现状缓解**：`--timeout N` 全局看门狗（v1.24.0）——伤害封顶，实测番茄现场 90s 准点强杀 exit 1。

**定位手段（下次修复从这里开始）**：
1. 每步 stderr 打"步名+开始/结束"分段计时（harvest/text/browser 各阶段入口出口），重跑两例看最后停在哪个步名
2. 挂死时用 `py-spy dump --pid <pid>` 抓 Python 栈（不用改代码，最直接的证据）
3. 重点怀疑对象（按可能性排序）：Playwright `expect_*`/locator 默认超时被覆盖为无限的位置、`browser.close()`/`context.close()` 对长连页面（WebSocket/SSE）的阻塞、`_wait_for_render` 之外的某个 evaluate 无 timeout 参数

**销账标准**：两例 URL 在无 `--timeout` 下 10 分钟内自行收口（成功或诚实失败均可）。

## 三、中严重度

### 问题 2：搜索浏览器死亡后无重建【需单跑复验】

**现象证据**：`--query "喜马拉雅 悬疑 播客" --auto` 压测：`[bing] error: Locator.count: Connection closed while reading from the driver` 后无后续引擎输出、无 JSON 产出（downloads/_stress_v124_ximalaya 记录）。

**定性理由**：单引擎异常有 try/except，但 "driver connection closed" = Chromium 进程/管道已死，同一 `page` 上后续引擎必然连环失败——缺"浏览器不可用→重启一次"的兜底。

**反问**：当时 3-4 个浏览器并行（压测批内），可能纯属资源挤兑。
**复验方案**：单独跑同一条命令（无并发）。复现 → 真 bug：browser.py `run_search` 每引擎前查 `browser.is_connected()`，断开则重启浏览器并重试当前引擎一次；不复现 → 降级为"并发场景已知限制"，写进 README 网络环境说明。

### 问题 4：引擎选择器零测试守护（工程债，先于一切选择器类修复）

**性质**：不是当前"错了什么"，而是"以后怎么改都心虚"。20 个轻量引擎是 HTML 正则、14 个浏览器引擎是硬编码选择器，站点改版即哑且无告警（v1.21.0 时代 alt.py 四个死引擎挂了几个版本才被人工发现）。
**方案**：为每个 HTML 引擎存一份真实响应夹具（tests/fixtures/engine_html/），测试断言"夹具→N 条结果且字段齐全"；浏览器引擎用录制页面/离线 DOM 断言。做一次，此后所有选择器修复都可回归。

## 四、低严重度 / 功能缺口

### 问题 3：own_search 倒排索引"只写不读"【bug（轻）】
`terms` 表建了（L205-239）但 `search_index`（L245-272）完全不查——每次查询全表载入内存做子串计数；SQLite 自带 FTS5 未启用。误导维护者 + 性能假象。**销账方案**：索引迁 FTS5（`CREATE VIRTUAL TABLE ... USING fts5`），查询走 MATCH；旧表保留迁移一次数据。

### 问题 5：搜索侧缺口（真新闻引擎 + 时间过滤）
`"news"` 分类 = 普通网页引擎+HN（engines/__init__.py:53），无 Bing News/NewsAPI 垂直、无时间排序；时间过滤连 arxiv/openalex/crossref 原生支持都没暴露。**方案**：先给 API 型引擎透传 `--since/--until`；再加一个 Bing News 垂直。

### 问题 6：own_search 功能缺口（增量重爬/URL 规范化去重/remove 命令/robots.txt）
非 bug，列此备忘。优先级排在 3 之后（FTS5 重构时可顺路做 URL 规范化）。

## 五、销账记录

### #2 → v1.25.0 处置（2026-09-28，搜索压测轮）：实锤比记载更严重，双层防护落地

**复验结论（压测 F/F2 实验，downloads/_search_stress/）**：
- F1（taskkill 杀 chromium）：无效实验——进程没死，后续引擎照常出结果，不能定级；
- F2（杀 playwright driver node 进程）：**实锤比"连环失败"更糟——driver 突死后 `page.goto` 永久挂起**（超时由 driver 执行，driver 死了没人执行），python 进程空转烧 CPU（实测 565s CPU-seconds），进程内调用无任何超时兜底。

**处置（不做进程内重启——sync API 线程绑定，driver 死后任何调用都可能挂起）**：
1. **子进程隔离**：auto_save 下载电路的搜索步（routing._search_first_media_url）从进程内直调 `searchkit.browser.run_search` 改走 `runner.run_search_cli` 子进程——超时有界（auto_timeout），挂死/崩溃不再波及下载宿主；
2. **快速失败**：browser.run_search 每引擎前查 `browser.is_connected()`，异常含 "connection closed" 类签名即标记后续引擎 "browser/driver dead (skipped)"，不再逐引擎白等超时。

**同轮压测附带成果**：跳转壳去重坍缩修复（百度 8 条→1 条误杀实锤）+ 壳解码、轻量引擎并发 2.2x、验证码识别、JS 失败场景定论——详见 README v1.25.0 更新记录。

### #1 → v1.24.1 根治（2026-09-24）：挂死真凶定位并消除，实测两例收口

**真凶（分段计时日志实测定位，非文档当初三个怀疑对象中的"某一步"，而是两层）**：
1. **`_extract_body_text` 的 selector 轮询黑洞**（主因）：旧实现用 `page.inner_text(sel)` 逐个试 11 个候选选择器，元素不存在时 Playwright 隐式等 selector 出现（默认 30s/个）。番茄阅读页全是自定义 div、11 个候选全 miss → 单章空耗 ~330s，351 章的书永远跑不完。签名与压测记录完全吻合（低 CPU 纯等待、零输出、目录页正常章节页卡死）。**修复**：改单次 JS 求值（`_BODY_TEXT_JS`）拿全部候选，一次往返零等待；再套 `_eval_bounded` 封顶。
2. **`browser.close()` 对长连页面阻塞**（次因，文档怀疑对象 ②确认）：番茄章节页挂着 WebSocket/SSE，`browser.close()` 无限阻塞。**修复**：`_close_bounded` 主线程三级顺序关闭 page → context → browser（实测番茄页面 0.7s 全清；线程方案已废弃——sync API 线程绑定，跨线程调用直接 greenlet 报错）。

**配套修复**：
- `_stage()` 分段计时日志：stderr 最后一条 `[stage]` 就是挂点，本次定位全靠它；
- `_eval_bounded()`：所有无 timeout 参数的 `page.evaluate` 封顶（wait_for_function 由 driver 强制超时，页面卡死也准点返回）；
- `_wait_for_render` 内部 evaluate 同步有界化。

**验证**：番茄全书 351/351 章实测收口（旧代码 300s 走不完 10 章，新代码每章 ~4s）；无 `--timeout` 下正常退出（销账标准达成）。
