## 二、高严重度（会崩溃 / 数据丢失 / 功能失效）

### 问题 1：verify_capture.py 无 ffmpeg 时 `--clean` 会删除所有正常视频【数据丢失风险】

**位置**：verify_capture.py L126-136（classify_file）、L187-200（clean_dir）

**代码证据**：

```python
# L126
real = _decoded_duration(str(path)) if _ffmpeg_path() else None
# L129-131
if real is None:
    if not _ffmpeg_path():
        item.update(verdict="broken", reason="无 ffmpeg,无法验证")
```

```python
# clean_dir：--clean 默认 also_broken=True
verdicts = {"junk"}
if also_broken:
    verdicts |= {"broken", "duration_inflated"}
# verdict==broken 的文件直接 unlink 删除
```

**问题**：机器上没装 ffmpeg 时，所有视频/音频的 `real` 都是 None → 全部判成 `broken` → 执行 `--clean`（不加 `--keep-broken`）时**把完好的正片全部删除**。

**影响**：SKILL.md 第 56 行还指导 AI "产物 broken → `verify_capture.py --clean` 清掉"，AI 在无 ffmpeg 的机器上照做会直接清空用户抓好的媒体文件。

**修复建议**：`clean_dir` 里加保护——`report["ffmpeg_found"]` 为 False 时拒绝删 broken/duration_inflated（只删 junk），并输出明确提示；或无 ffmpeg 时 verdict 用 `unverified` 而不是 `broken`。

### 问题 2：search_and_cache.py 子进程超时未捕获，超时即整体崩溃

**位置**：search_and_cache.py L44-51（run_search）、L75-82（cache_url）

**代码证据**：

```python
# L44-51：subprocess.run 不在 try 里，只有 json.loads 在 try 里
proc = subprocess.run(cmd, capture_output=True, text=True,
                      encoding="utf-8", errors="ignore", timeout=120)
try:
    return json.loads(proc.stdout or "{}")
except Exception:
    ...
```

**问题**：`subprocess.run` 抛出的 `TimeoutExpired` 没有任何捕获，直接冒泡到 main() → **整个脚本带堆栈崩溃**。而超时在这里很容易发生：

- `run_search` 给 smart_search 120s，但 smart_search 最多跑 2 轮分类 × 每轮 90s = 180s；
- `cache_url` 给 auto_save_browser 180s，但 chain 模式内部 `--max-wait` 默认就是 180s，加上滚动/收割/合并，视频页常规耗时就会超过 180s。

**影响**：`--download`（chain）或浏览器搜索慢一点，用户看到的就是 Python traceback 而不是 JSON 结果，违反项目"优雅降级输出 JSON 不崩溃"的规则。对照 cross_search.py 的同类调用（L70-81）是把 `subprocess.run` 整个包在 try 里的，唯独 search_and_cache.py 漏了。

**修复建议**：把两处 `subprocess.run` 包进 try/except，超时/异常时返回 `{"error": ...}` 继续下一个 URL；同时把 cache_url 的 timeout 提到 ≥300s（或按 `--max-wait` 传递）。

### 问题 3：own_search.py `download --safe` 参数无效（接受但从不传递）

**位置**：own_search.py L306-321（cmd_download）、L416（参数定义）

**代码证据**：

```python
# L416 定义了参数
p_download.add_argument("--safe", action="store_true", help="安全模式：...")
# L309-315 但 cmd 里根本没有 --safe
cmd = [sys.executable, str(script), "--json"]
if args.url:   cmd += ["--url", args.url]
elif args.query: cmd += ["--query", args.query, "--auto"]
if args.output_dir: cmd += ["--output-dir", args.output_dir]
```

**问题**：`--safe` 被 argparse 接受，但 `cmd_download` 拼命令时从未把 `--safe` 传给 auto_save_browser.py。用户以为开了安全模式，实际跑的是普通模式（无沙箱、无拦截、无落盘白名单）。

**影响**：安全功能静默失效，属于"用户以为受保护但实际没有"的最坏一类。SKILL.md 第 324 行还明确写了用法 `own_search.py download --query "..." --safe`，文档与实现不符。

**修复建议**：`cmd_download` 里加 `if args.safe: cmd.append("--safe")`。

## 三、中严重度（特定场景功能受损 / 文档不符）

### 问题 4：smart_search.py 子进程 90s 超时对浏览器版不够

**位置**：smart_search.py L89-96（run_attempt）

**代码证据**：`subprocess.run(cmd, ..., timeout=90)`；而 search_browser.py 每个引擎最坏 `goto 25s + wait_for_selector 10s + sleep ~1.2s + 引擎间隔 ~0.8s ≈ 36s`。

**问题**：浏览器版 finance 分类有 3 个引擎（最坏 ~110s > 90s），all 分类 9 个引擎必然超。超时后整轮被当成"subprocess 异常"，换分类重试也大概率再超 → 最终返回空结果（普通情况几十秒能完成，只在引擎慢时触发，属于间歇性全失败）。

**修复建议**：按引擎数动态计算超时（如 `30 + 引擎数 × 40` 秒），或浏览器版放宽到 240s。

### 问题 5：cross_search.py mega 模式超时不足且失败静默

**位置**：cross_search.py L105-117（run_full_copy，timeout=120）

**问题**：
1. `--category all` 在轻量版是 17 个引擎、浏览器版 9 个引擎，最坏情况远超 120s → `TimeoutExpired` → `except Exception: return []`，**整份结果为空且无任何错误信息**；
2. mega 的 rounds_info 只记 `raw_results: 0`，调用方无法区分"搜不到"和"超时被杀"。

**修复建议**：超时按引擎数放大；捕获超时时至少 stderr 记录一条 `[copy] timeout`，rounds_info 里加 `timed_out` 标记。

### 问题 6：URL 去重丢弃全部 query 参数，误杀不同页面

**位置**：search.py L98-109、search_browser.py L91-102（`_normalize_url`，两文件相同实现）

**代码证据**：`return f"{host}{path}"` —— query 和 fragment 完全不参与 key。

**问题**：对"路径相同、参数不同"的页面，第二条会被当成重复丢掉。典型受害场景：
- YouTube：`youtube.com/watch?v=aaa` 与 `youtube.com/watch?v=bbb` → key 都是 `youtube.comwatch`，**同一批搜索结果里只能留下一条 YouTube 视频**；
- 淘宝/知乎/百度贴吧等大量依赖 query 参数的站点同理。

**影响**：搜索聚合结果被系统性削薄，且用户难以察觉。

**修复建议**：保留有业务含义的 query（白名单方式保留 `v/id/p/tid` 等常见内容参数），或 key 相同时再比对标题/摘要相似度决定是否合并，而不是直接砍。

### 问题 7：README 版本号与 package.json / SKILL.md 不同步

**位置**：README.md L7、README.zh-CN.md L7

**证据**：
- README.md / README.zh-CN.md：`Current version v1.12.0 (2026-08-21)`
- package.json：`"version": "1.12.1"`；SKILL.md：`version: 1.12.1, updated: 2026-08-21`

**问题**：项目规则要求"版本号在 SKILL.md 和 package.json 间同步、README 含版本号+更新时间+作者"。现在 README 落后一个版本；且 v1.12.1（视觉会话 10 项修复）实际完成于 2026-08-22，SKILL.md 的 updated 日期仍写 08-21；README 两语言版均无作者信息。

**修复建议**：发版前把两份 README 更新到 v1.12.1 + 2026-08-22，补作者与 v1.12.1 变更记录。

### 问题 8：财经引擎组与项目规则不符

**位置**：search.py L666、search_browser.py L438、SKILL.md L348

**证据**：
- 项目规则：财经意图应使用专业财经引擎组（东方财富、集思录、财新）；
- search_browser.py finance = `["eastmoney", "bing", "sogou"]` —— 有东方财富，**没有集思录、财新**；
- search.py finance = `["yahoo_finance", "bing", "sogou", "so360", "baidu"]` —— **完全没有东方财富**（轻量版走 Yahoo Finance+通用引擎，仍可能吃到竞价广告）。

**问题**：SKILL.md L348 写"财经搜索 v1.9.0 起东方财富专业站打头"，但该描述只对浏览器版成立；轻量版（smart_search 不加 --browser 时走 search.py）财经意图根本用不上东方财富。

**修复建议**：确认产品意图——要么给 search.py 财经分类补东方财富的 HTTP 可抓入口（或至少在 SKILL.md 标注"仅浏览器版"），要么调整规则表述；集思录/财新如果没计划做，从规则里移除。

### 问题 11：`--query --auto` 模式缺少退回 chain 的兜底

**位置**：auto_save_browser.py L3522（--url 模式有兜底）vs L3552-3607（--query --auto 模式没有）

**问题**：`--url` 自动选路（harvest/files/text）颗粒无收时会打印"退回 chain 通用链重试"再跑一遍 chain；`--query --auto` 同样会自动选到 harvest/files/text 专用线，但失败后**没有**这个兜底，直接报"没有收获"。两条入口行为不一致。

**修复建议**：query 模式失败后同样退回 chain 重试一次，或明确文档说明差异是有意的。

### 问题 12：mega 模式显式传默认引擎串会被静默换成全引擎

**位置**：cross_search.py L499

```python
engines_csv=",".join(engines) if args.engines and args.engines != ",".join(DEFAULT_ENGINES) else "",
```

**问题**：用户显式输入 `--engines so360,sogou,bing`（恰好等于默认串）时，条件判断把它当成"用户没指定"，实际执行 `--category all` 全引擎。用户的显式选择被静默覆盖。

**修复建议**：用 `argparse` 的 `default=None` + 事后判空来区分"没传"和"传了默认值"。

### 问题 13：concat 失败可能留下半成品文件

**位置**：verify_capture.py L226-232（assemble_segments）

**问题**：ffmpeg returncode != 0 时直接 return 错误，但 `-y` 模式下 ffmpeg 可能已创建不完整的 out_path，没有清理（成功路径有清理逻辑，失败路径没有）。

**修复建议**：失败分支里 `out_path.unlink(missing_ok=True)`。

### 问题 14：`_resolve_engines` 两文件参数顺序相反

**位置**：search.py L724 `def _resolve_engines(explicit, query, category="general")` vs search_browser.py L550 `def _resolve_engines(explicit, category="general", query="")`

**问题**：同名函数参数顺序相反。目前两个文件内部调用各自正确（auto_save_browser.py L835 调的是浏览器版 `("", "general")` 恰好没踩坑），但任何人跨文件复制调用代码都极易把 query 传成 category。

**修复建议**：统一两边签名（建议都改成 keyword 调用）。
