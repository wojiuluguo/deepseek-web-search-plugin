# 工作方法与开发习惯（对话中实际运用、未曾落文的总结）

> 来源：主项目开发对话上下文（2026-08 ~ 2026-10-16 全程）。
> 与《对话沉淀经验_2026-10-16.md》（技术结论）互补——那份记"学到了什么"，这份记"我怎么干活"。
> 写代码前过一遍；与 [../03-双方融合经验/](../03-双方融合经验/) 对照使用。

## A. 接任务的流程

1. **先摸现状再动手**：改文档前先 grep 标题结构 / 数行数（CHANGELOG 拆分前先确认"更新记录占 280 行/一半篇幅"才决定方案）；改代码前先读目标函数与周边调用。
2. **任务拆分挂账**：大任务用 TodoWrite 拆成可勾销的小步，做完一项勾一项——多轮长对话不丢线索。
3. **大文件不全量读**：先读结构（标题/关键行号），再精读目标区段——省上下文也省得起走神。
4. **边界意识**：协作文档分清归属——子服务的 BUGS.md 只读不改，裁决与记录写进自己的文档；同构复制体（对方 skill 快照）只同步不修订。

## B. 修改代码的纪律

5. **构造性复现先于修复**：修前先写出能稳定触发 bug 的最小场景（如 rc=1+合法 JSON / rc=0+空 stdout → `data={}` 被当成功 → 消费方 KeyError），修复后再跑同一场景确认消除。
6. **证据普查代替印象**：声称"防护为零/存在缺口"前先 grep 全仓（隐形字符 17 种模式 0 命中——这就是实锤）；声称"有活调用"也用 grep 证明（死代码指控的驳回依据）。
7. **兼容面盘点**：改共享件（envelope/runner/公共函数）语义后，逐个列出全部消费方核清影响——4 个消费方中仅 smart_search 行为变化且是走设计好的分支，这才允许合入。
8. **一个入口出缺口，查所有兄弟入口**：`--hosts` 绕私网实锤后连带查同类——发现 file:// 走 Playwright 兜底还能绕过第一层白名单，遂改双层设防；同类问题不会只存在于被举报的那一处。
9. **复制体先 grep**：动共享实现前先搜有没有副本（看门狗上收 runner 时顺带消灭 auto_save_browser 门面里的重复副本）；消灭不了的要写清"谁是唯一真源"。
10. **移植不照抄**：跨项目搬模块先对比架构差异（子服务 sanitize 在 server 出口、主项目无 server → 改接聚合源头），照抄会把不适配的结构一起搬进来。
11. **修复必配测试**：每轮修复新测试文件跟着走（22 项/21 项），收工标准 = `tests/run_all.py` 全绿；对方指定的验收用例直接固化进自己的回归。
12. **修 bug 顺带灭同类债务**：审计点名一份重复实现，上收实现时把门面副本一并清掉；改 dispatch 顺带对齐已知的 QA-1 表述。

## C. Git / 发版操作

13. **git add 按名单逐个加**，不用 `add -A`/`add .`——防误加敏感文件与无关产物。
14. **长 commit message 走临时文件** `git commit -F`（PowerShell 无 heredoc）；push 用 `git push origin HEAD` 不猜分支名。
15. **推完必复核**：`git ls-files` 审清单（子项目文件夹必须 0 条）；zip 用 `git archive` 打（天然继承 .gitignore），打完列出条目肉眼过一遍再上传。
16. **版本号四处同步**：SKILL.md、package.json、双语 README 头部、CHANGELOG——少一处就是 v1.12.1 时代的版本漂移旧病。

## D. 工具与环境用法

17. **PowerShell 环境三条铁律**：不支持 heredoc；`python -c` 内联多行代码转义易炸（改写临时脚本放 %TEMP% 用完删）；Set-Content 会改写换行符（批量改文档用 Python 保 `newline=''`）。
18. **行级大范围重组用脚本，小改动用 Edit**：280 行的节替换手写 old_string 必错，按标题定位边界 + 切片重组更稳。
19. **建好目录必列目录树核对**：复制/新建后 `Get-ChildItem -Recurse` 亲眼确认文件都在、大小正常，不信"命令没报错就是对了"。
20. **测试内 patch 优于命令行注入**：验证函数行为在测试进程里替换依赖（FakeProc），不靠 `python -c` 从外面塞——转义炸过才知道。

## E. 沟通与汇报

21. **先答案后过程**：回复先给结论/表格，细节往后放；用户偏好表格 over 长段落。
22. **拟改动先给方案等确认**："能不能/怎么样"是征询，确认后再动手；但用户给过"确认是 bug 直接修"的授权范围除外。
23. **裁决透明**：修复与搁置都要留痕——搁置的写"为什么不是 bug + 证据 + 观察计划"，不是悄悄跳过。
